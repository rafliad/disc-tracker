# M6 status Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Update owned job applications, Forum tags, displayed status and history through `/status`.
**Architecture:** Signed Worker interactions, existing D1 and Discord REST. Durable interaction claims serialize updates and preserve uncertain outcomes for manual checking.
**Tech Stack:** TypeScript, Cloudflare Workers/D1, Discord REST, Vitest, Node CLI.
**Spec:** ../specs/2026-10-11-status-design.md

## Global Constraints

- Exactly seven statuses: Applied, Screening, Assessment, Interview, Offer, Rejected, Withdrawn.
- Only guild-authorized owners; preserve current private routing secrets and Ed25519 verification.
- No new dependencies/services/secrets or commands beyond `/status`.
- Never log tokens, URLs, raw Discord errors, or application text.
- Reject redirects through supported Workers `manual` mode; validate actual Request options in tests.

## Review Focus

- Replays after a newer change must not revert the application or duplicate history.
- Concurrent requests must not interleave Discord mutations.
- Thread parent/guild mismatches must produce zero Discord writes.
- A timeout after a write may mean it succeeded; retain the claim and explain uncertainty.
- Archived/locked posts must have their original state restored, or report partial failure.
